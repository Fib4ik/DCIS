# Журнал архітектурних рішень (ADR)

У цьому документі зафіксовані ключові архітектурні рішення (Architecture Decision Records), прийняті під час проектування "Платформи доставки їжі". Кожен запис описує контекст проблеми, проаналізовані альтернативи, прийняте рішення та його позитивні й негативні наслідки.

---

## ADR-001: Вибір мікросервісної архітектури замість моноліту

### 1. Контекст
Платформа доставки їжі має кілька незалежних напрямків бізнес-логіки з різним характером навантаження:
* Пошук та перегляд меню (високе читацьке навантаження).
* Обробка замовлень та оплати (критична вимогливість до надійності).
* Геотрекінг кур'єрів у реальному часі (високе частотне запсування/читання).

Окрім цього, пікові навантаження припадають на обідні та вечірні години. При виникненні збоїв в одному модулі (наприклад, у системі відгуків) замовлення їжі зупинятися не повинно.

### 2. Розглянуті варіанти
* **Варіант A: Монолітна архітектура (Monolithic)**
  * *Плюси:* Простіша розробка на початковому етапі, легше розгортання єдиного репозиторію, відсутність мережевих затримок між модулями.
  * *Мінуси:* Складність масштабування окремих частин; падіння одного модуля завалює увесь застосунок; висока зв'язаність коду при зростанні команди.
* **Варіант B: Мікросервісна архітектура (Microservices)**
  * *Плюси:* Незалежне масштабування та деплой кожного сервісу; відмовостійкість (ізоляція збоїв); можливість обирати різні стеки технологій під конкретні задачі.
  * *Мінуси:* Складність інфраструктури, виклики з узгодженістю даних (Eventual Consistency), складніше відлагодження (distributed tracing).

### 3. Прийняте рішення
Обрати **Мікросервісну архітектуру** (Варіант B) з виділенням core-сервісів: *Catalog Service*, *Order Service*, *Payment Service*, *Delivery Service* та *Notification Service*.

### 4. Наслідки
* **Позитивні:** Сервіс трекінгу кур'єрів можна масштабувати окремо під час піків, не витрачаючи ресурси на сервіс каталогу. Збій у сервісі відгуків не заважає оплаті та доставці.
* **Негативні:** Потрібно впровадити API Gateway, брокер повідомлень та інструменти моніторингу/трасування (Prometheus, Jaeger).

## ADR-002: Вибір бази даних для замовлень та каталогу

### 1. Контекст
Для збереження транзакційних даних (замовлення, платежі, структуроване меню з фіксованими цінами) потрібне надійне сховище, яке підтримує суворі гарантії цілісності даних (ACID). Водночас для швидкого кешування та пошуку меню потрібна мінімальна затримка.

### 2. Розглянуті варіанти
* **Варіант A: Єдина NoSQL БД (MongoDB)**
  * *Плюси:* Гнучка схема даних для страв та модифікаторів, висока швидкість запису.
  * *Мінуси:* Складніша організація багатокрокових фінансових транзакцій, відсутність строгих реляційних зв'язків.
* **Варіант B: Реляційна БД (PostgreSQL) + Кешування (Redis)**
  * *Плюси:* Надійна підтримка ACID-транзакцій для замовлень, потужні інструменти роботи з SQL, підтримка JSONB. Redis забезпечує надшвидкий доступ (In-Memory) до списку меню та сесій.
  * *Мінуси:* Необхідність проектування та підтримки схем міграцій БД; додаткові витрати на підтримку Redis-кластера.

### 3. Прийняте рішення
Використовувати **PostgreSQL як основну реляційну БД** для сервісів замовлень та каталогу, у поєднанні з **Redis для кешування** часто запитуваних даних меню та гарячих даних геолокації.

### 4. Наслідки
* **Позитивні:** Гарантована цілісність фінансових чеків та замовлень. Завдяки кешуванню меню в Redis швидкість відгуку при пошуку їжі становить < 50 мс.
* **Негативні:** Потрібно контролювати інвалідацію кешу в Redis при оновленні цін або стоп-листа в PostgreSQL.

## ADR-003: Вибір брокера повідомлень для асинхронних сповіщень та подій

### 1. Контекст
Система генерує велику кількість подій: "Замовлення створено", "Оплата успішна", "Кур'єр обрав маршрут". Супутні сервіси (Сповіщення, Аналітика, Кабінет ресторану) мають реагувати на ці події асинхронно, не уповільнюючи процес оформлення.

### 2. Розглянуті варіанти
* **Варіант A: RabbitMQ**
  * *Плюси:* Гнучка маршрутизація повідомлень (Exchange types: direct, topic, fanout), простота налаштування, відмінно підходить для задач типу "Task Queue" (наприклад, надіслати push-сповіщення конкретному користувачу).
  * *Мінуси:* Менша пропускна здатність порівняно з Kafka при мільйонних потоках логів; повідомлення видаляються після обробки.
* **Варіант B: Apache Kafka**
  * *Плюси:* Надвисока пропускна здатність, збереження історії подій (Event Sourcing), можливість повторного програвання (replay) подій.
  * *Мінуси:* Високий поріг входження, складність налаштування та адміністрування ZooKeeper/KRaft.

### 3. Прийняте рішення
Обрати **RabbitMQ** як основний брокер повідомлень для міжсервісної взаємодії (Event-Driven Communication) та задач сповіщення на даному етапі розвитку платформи.

### 4. Наслідки
* **Позитивні:** Швидке впровадження гнучкої системи черг для відправки SMS, Push та оновлення статусів у реальному часі. Просте адміністрування командою.
* **Негативні:** У майбутньому, при переході до глибокої аналітики великих даних (Big Data Streaming), можливо, доведеться додати Apache Kafka.

## ADR-004: Вибір способу узгодженості даних при оплаті (Saga та Eventual Consistency)

### 1. Контекст
Процес замовлення охоплює кілька сервісів (*Order Service*, *Payment Service*, *Delivery Service*). Оскільки кожен мікросервіс має свою базу даних, створення єдиної 2PC-транзакції (Two-Phase Commit) неможливе через низьку продуктивність та високий ризик блокувань.

### 2. Розглянуті варіанти
* **Варіант A: Двофазний комміт (2PC / Distributed Transactions)**
  * *Плюси:* Строга узгодженість (Strong Consistency) "тут і зараз".
  * *Мінуси:* Довгі блокування ресурсів у базах даних, низька відмовостійкість — якщо один сервіс не відповідає, блокується весь ланцюг.
* **Варіант B: Патерн Saga (Оркестрація) + Підсумкова узгодженість (Eventual Consistency)**
  * *Плюси:* Висока доступність та швидкодія. Кожен сервіс виконує локальну транзакцію. У разі помилки виконуються скасовуючі (компенсуючі) дії.
  * *Мінуси:* Дані стають повністю узгодженими не миттєво, а через короткий проміжок часу (Eventual Consistency). Складніша логіка обробки помилок.

### 3. Прийняте рішення
Впровадити **патерн Saga з централізованим Оркестратором** на базі *Order Service*.

### 4. Наслідки
* **Позитивні:** Відсутність довготривалих блокувань у БД, система залишається чутливою навіть при тимчасових затримках окремих сервісів.
* **Негативні:** Необхідність проектування та ретельного тестування компенсуючих дій для кожного кроку (наприклад, повернення коштів на картку при відсутності кур'єрів).

## ADR-005: Вибір алгоритму розрахунку вартості доставки

### 1. Контекст
Ціна доставки не може бути фіксованою, оскільки вона залежить від відстані між рестораном та клієнтом, заторів на дорогах, часу доби та погодних умов (дощ, сніг), а також поточного балансу попиту й пропозиції (кількість активних замовлень проти кількості кур'єрів на лінії).

### 2. Розглянуті варіанти
* **Варіант A: Фіксована вартість або зональна тарифна сітка**
  * *Плюси:* Гранична простота реалізації, зрозумілість для клієнта.
  * *Мінуси:* Збитковість для платформи під час складних/далеких доставок у години пік; відсутність стимуляції для кур'єрів виходити на зміну в негоду.
* **Варіант B: Динамічний ціноутворювальний алгоритм (Dynamic Surge Pricing)**
  * *Формула:* `Base_Fee + (Distance * Rate) + Weather_Surge + Traffic_Surge + High_Demand_Surge`
  * *Плюси:* Автоматичне коригування ціни. У пікові години підвищений тариф залучає більше кур'єрів і регулює потік замовлень, зберігаючи маржинальність бізнесу.
  * *Мінуси:* Складніший алгоритм, необхідність обробляти дані про погоду та затори в реальному часі.

### 3. Прийняте рішення
Впровадити **Динамічний алгоритм розрахунку вартості (Dynamic Surge Pricing)** у складі *Delivery Service*.

### 4. Наслідки
* **Позитивні:** Економічна збалансованість платформи. Забезпечення високого відсотка успішних доставок у пікові години за рахунок мотивації кур'єрів.
* **Негативні:** Потрібна інтеграція з API погодних сервісів та карт (Google Maps / OpenStreetMap), а також прозорий інформер у мобільному застосунку, який пояснює клієнту причину тимчасового підвищення тарифу.
